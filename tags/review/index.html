一、数据模型总论

  1. 数据模型的定义
    数据模型是用来抽象、表示和处理现实世界中的数据和信息的工具，本质上是对现实世界数据特征的抽象。它是数据库研究中的核心问题之一。

  2. 数据模型的两层含义
    广义上，数据模型是数据库研究的核心；狭义上，每个 DBMS 都建立在某种具体的数据模型之上。PDF 指出，常见的传统数据模型包括层次模型、网状模型和关系模型。

  3. 数据模型的分类
    数据模型按应用目的可分为两类：
    （1）概念模型，也称信息模型，按用户观点对数据和信息建模，主要用于数据库设计。
    （2）数据模型，按计算机系统观点对数据逻辑结构建模，主要用于 DBMS 实现。其下又可分为逻辑数据模型和物理数据模型。逻辑数据模型包括层次模型、网状模型、关系模型、面向对象模型、对象关系模型等；物理数据模型描述数据在系统内部的表示方式和存取方法。

  4. 数据模型的三个要素
    数据模型通常由数据结构、数据操作、完整性约束三个要素组成。
    （1）数据结构：描述数据库的组成对象及对象之间的联系，是刻画数据模型性质最重要的方面。
    （2）数据操作：描述对数据库对象实例允许执行的操作集合，包括检索、插入、删除、修改等，同时要定义操作的含义、符号、规则及语言。
    （3）完整性约束条件：一组完整性规则，用于限定符合数据模型的数据库状态及状态变化，保证数据正确、有效、相容。

  5. 静态与动态特性
    数据结构描述系统静态特性；数据操作描述系统动态特性。完整性约束则是保证系统状态合法的规则体系。

二、E-R 概念模型

  1. 概念模型的作用
    概念模型用于信息世界建模，是现实世界到机器世界之间的中间层次，也是数据库设计的有力工具和数据库设计人员与用户之间交流的语言。它的要求是语义表达能力强，同时简单、清晰、易于理解。E-R 模型是最著名的概念模型。

  2. E-R 模型的三大基本概念
    （1）实体（Entity）：客观存在并可相互区别的事物，可以是具体对象，也可以是抽象概念。
    （2）属性（Attribute）：实体具有的某一特征，用来刻画实体。属性有“型”和“值”之分，属性名是型，具体内容是值。
    （3）联系（Relationship）：现实世界中事物内部以及事物之间的联系，在信息世界中抽象为实体内部的联系和实体之间的联系。

  3. 联系的基本类型
    （1）一对一联系（1:1）：实体集 A 中一个实体至多对应实体集 B 中一个实体，反之亦然。例子是“班级与班长”，一个班级只有一个正班长，一个班长只在一个班中任职。
    （2）一对多联系（1:n）：实体集 A 中一个实体对应实体集 B 中的多个实体，反过来一个 B 中实体至多对应一个 A 中实体。例子是“班级与学生”，一个班级中有若干学生，一个学生只在一个班级中学习。
    （3）多对多联系（m:n）：实体集 A 中一个实体对应实体集 B 中多个实体，反之亦然。例子是“课程与学生”，一门课程有若干学生选修，一个学生也可选修多门课程。

  4. 多元联系
    两个以上实体集之间也可以存在联系，称为多元联系。PDF 以“供应商—零件—工程”为例，说明三者之间存在 m:n:p 的联系，表达的是“某个供应商供应某种零件给某个工程”。

  5. 三元联系与二元联系的区别
    这是本章非常关键的细节。PDF 明确指出，三个实体集两两之间的多对多联系，只能表示“一个工程需要哪些零件”“这些零件可以由哪些供应商供应”，却不能表示“一个工程所用的零件具体由哪个供应商供应”以及“一个供应商具体供应哪种零件给哪个工程”。因此，三元联系不能简单拆成三个二元联系，否则会丢失语义。

  6. 同一实体集内部的联系
    PDF 还强调，联系不只存在于不同实体集之间，同一实体集内部也可以有联系。典型例子是职工实体集内部的“领导与被领导”关系：某一职工可以领导若干职工，而一个职工仅被另一个职工直接领导，这是同一实体型内部的一对多联系。PDF 也提到，同一实体集内部还可能存在一对一联系和多对多联系。

  7. E-R 图的表示方法
    E-R 图有三个基本成分：实体、属性和联系。
    （1）实体用矩形表示，矩形框内写实体名。
    （2）属性用椭圆表示，并用无向边与对应实体连接。
    （3）联系用菱形表示，菱形框内写联系名，再用连线把关联实体连接起来，并在连线旁标明联系类型 1:1、1:n 或 m:n。

  8. 联系的属性
    联系本身也可以有属性。PDF 的“选课”例子中，成绩是联系“选课”的属性，而不是学生实体或课程实体的属性，因为成绩描述的是“学生选修某门课程”这个联系。

  9. 弱实体
    弱实体是一类特殊实体，它的存在依赖于其他实体而存在。与弱实体相对应，所依赖的实体称为强实体。弱实体在 E-R 模型中用双框矩形表示，与菱形联系间用双线连接，以表示全部参与。PDF 举例说，在学生管理信息中，家长实体依赖学生实体存在，因此家长可视为弱实体。

  10. 子类实体
    扩展 E-R 模型中增加了子类和超类概念，使模型更有语义表达能力。一个实体集中的个体可以根据不同特性划分为多个子集。PDF 的例子是学校一个系的职工可分为教师、实验人员和机关工作人员，它们共享姓名、年龄、性别等共同属性，同时又有各自的特殊属性。

  11. E-R 模型的用途与特点
    E-R 模型广泛用于数据库概念模型设计。它只表示现实世界中的信息结构及信息之间的关系，不涉及信息在计算机中的表示；只要用户需求不变，E-R 模型是稳定的，并且可以方便地转换成具体 DBMS 支持的数据模型。

  12. PDF 中的综合建模例子
    工厂物资管理模型是本章最完整的例子之一。它涉及五类实体：仓库、零件、供应商、项目、职工。
    （1）仓库：仓库号、面积、电话号码。
    （2）零件：零件号、名称、规格、单价、描述。
    （3）供应商：供应商号、姓名、地址、电话号码、账号。
    （4）项目：项目号、预算、开工日期。
    （5）职工：职工号、姓名、年龄、职称。
    这些实体之间的联系包括：仓库和零件是 m:n 联系，联系属性为库存量；仓库和职工是 1:n 联系；职工内部存在领导与被领导的一对多联系；供应商、项目和零件三者之间存在多对多的三元联系。这个例子综合体现了本章几乎所有 E-R 概念。

三、层次数据模型

  1. 层次模型的定义
    层次模型是数据库系统中最早出现的数据模型，典型代表是 IBM 的 IMS。它用树型结构表示各类实体及实体间联系。现实世界中许多关系具有天然层次性，例如家族关系和行政机构。

  2. 层次模型的结构条件
    满足下面两个条件的基本层次联系集合构成层次模型：
    （1）有且只有一个结点没有双亲结点，该结点称为根结点。
    （2）根以外的其他结点有且只有一个双亲结点。

  3. 层次结构中的术语
    根结点位于最上层；其他结点的上一级结点称为双亲结点；同一双亲结点的子女结点称为兄弟结点；没有子女的结点称为叶结点。双亲结点到子女结点之间表示记录间的一对多联系。

  4. 层次模型的优点
    结构简单清晰；查询效率高；提供较好的数据完整性支持。

  5. 层次模型的缺点
    不能直接表示两个以上实体型间的复杂联系和实体型间的多对多联系，通常要通过引入冗余数据或虚拟结点来解决，容易产生不一致性；插入和删除操作限制较多；查询子女结点必须通过双亲结点；由于结构严密，层次命令趋于程序化。

四、网状数据模型

  1. 网状模型的定义
    网状模型用有向图表示实体及实体间的联系，是对层次模型局限性的突破。现实世界中的许多事物之间是非层次关系，因此网状模型比层次模型更接近实际。

  2. 网状模型的结构条件
    基本网状模型满足两个条件：
    （1）允许一个以上的结点没有双亲。
    （2）一个结点可以有多于一个的双亲。

  3. 网状模型与层次模型的关系
    PDF 明确指出，层次模型实际上是网状模型的特例。两者从结构上看，层次模型是树，网状模型是图；当多个结点都可以有多个双亲时，有向树就变成了有向图。

  4. 网状模型的优点
    能更直接地描述现实世界，例如一个结点可以有多个双亲；性能较好，存取效率较高。

  5. 网状模型的缺点
    结构复杂，随着应用环境扩大，数据库结构会越来越复杂，不利于最终用户掌握；DDL、DML 语言复杂，用户不容易使用；访问数据时必须自行选择存取路径，增加程序编写负担。

  6. 网状模型如何表示多对多联系
    PDF 提到，网状模型可以间接表示多对多联系，方法是将多对多联系分解成一对多联系，并用联结记录来处理。

五、关系数据模型

  1. 关系模型的重要地位
    关系模型是最重要的数据模型。E.F. Codd 于 1970 年系统而严格地提出关系数据模型，并随后提出关系代数、关系演算以及关系范式理论，奠定了现代数据库的理论基础，1981 年因此获得图灵奖。

  2. 关系数据库的发展
    PDF 提到，1977 年 IBM 的 System R 开始运行，后来出现了基于 System R 的 SQL/DB。20 世纪 80 年代以来，几乎所有数据库管理系统都支持关系模型，非关系系统也增加了关系接口；当前数据库研究工作也以关系方法为基础，关系数据库成为最广泛应用的数据库系统。

  3. 关系模型的基本结构
    关系模型中，基本数据结构被限制为二维表，一张二维表称为一个关系。一个关系可用于描述一个实体集。

  4. 关系模型中的基本术语
    （1）关系（relation）：二维表，由行和列组成。
    （2）属性（attribute）：关系中的一列。
    （3）域（domain）：某属性的取值集合，即属性的取值范围。
    （4）元组（tuple）：关系中的一行，表示实体集中的一个个体。
    （5）键（key）：一个或多个属性组成，能够唯一标识一个元组。一个关系中可能有多个键，其中选定一个为主键，其余为候选键。

  5. 关系模式
    对关系结构的描述称为关系模式，形式通常写作“关系名(属性名1, 属性名2, …, 属性名n)”。例如学生关系可表示为“学生(学号, 姓名, 出生年月, 性别, 入学年份, 班级)”。关系数据库模式是一组关系模式的集合，而这些关系模式对应的关系集合构成关系数据库。

  6. 关系模型中实体与联系的表示
    关系模型中，基本数据结构是单一的关系，现实世界中的实体以及实体间的联系都用关系表示。E-R 模型中的联系在关系模式中也可以用表表示，例如“选课”联系可用“选课(学号, 课程号, 成绩)”表示，其中成绩是联系自身的描述属性。

  7. 关系模型的规范化要求
    关系必须规范化，最基本的规范条件是：关系的每一个分量必须是一个不可分的数据项。PDF 用“职工工资”表说明，如果一个属性中又包含“基本工资、工龄、职务、房租、水电”等嵌套成分，就不符合关系模型要求。

  8. 关系模型的数据完整性约束
    为维护数据库与现实世界的一致性，需要对数据施加约束条件。关系模型中主要有三类完整性约束：实体完整性、参照完整性、用户自定义完整性。

  9. 关系模型的数据操纵
    关系模型中的数据操作包括查询、插入、删除和修改。关系数据库系统中对数据的全部操作都可以归结为关系运算；关系运算结果形成一个新关系；关系运算分为关系代数和关系演算。

  10. 关系模型的优点
    PDF 归纳的关系模型优点包括：数据结构简单；一体化的数据子语言；数据独立性高；面向集合的存取方式；理论基础坚实；有利于开展其他应用。

  11. 概念模型与关系数据模型的对应
    PDF 给出了一组非常重要的对应关系：
    （1）E-R 模型中的实体集对应关系表。
    （2）实体集属性对应表的列。
    （3）联系集及其属性也可对应表和列。
    （4）实体的实例对应表中的各行。
    （5）主键或候选键对应关系表中的主键或候选键。
    （6）数据操作在实现层面对应 SQL 语句，在理论层面对应关系代数和关系演算。
    （7）联系类型约束、键约束、完全参与约束在关系模型中分别对应实体完整性、参照完整性和用户自定义完整性。

六、面向对象数据模型

  1. 面向对象数据库系统的两条路线
    PDF 指出，对象关系数据库系统 ORDBS 是面向对象数据模型和关系数据模型结合的产物。研究路线有两条：一是建立新的面向对象数据库系统 OODB，直接支持 OO 数据模型；二是以关系数据库和 SQL 为基础，把面向对象技术融入数据库系统，形成 ORDBS。

  2. 对象的定义
    对象是由一组数据结构和在这组数据结构上的操作程序代码封装起来的基本单位。对象由属性集合和方法集合构成：属性描述状态、组成和特性，方法描述行为特性。

  3. OID
    OID 是对象标识符，即每个对象都有一个唯一且不变的标识。它具有永久持久性、独立于值、系统全局唯一等特点。

  4. 封装
    封装是对象的外部界面与内部实现之间实行清晰隔离的一种抽象，外部与对象的通信只能通过消息。对象封装后，查询属性值必须通过调用方法。

  5. 类
    类是共享同样属性和方法集的所有对象构成的集合。对象是某一类的实例，在 OODB 中，类是“型”，对象是某一类的“值”。

  6. 类层次结构
    PDF 以“教员、行政人员、工人继承教职员工类和人的属性与方法”为例，说明面向对象模型中存在类层次结构；子类在逻辑上继承父类的所有属性和方法，同时还拥有自身特有的属性和方法。

  7. 关系模型与 OO 模型的比较
    PDF 从多个角度对比两者：关系模型的基本数据结构是二维表，OO 模型是类；关系模型使用码作为标识，OO 模型使用 OID；关系模型的动态行为用关系操作描述，OO 模型用方法描述；OO 模型支持抽象数据类型和封装，而关系模型没有；关系模型主要依赖主外码联系和数据依赖，OO 模型则强调继承和组合；OO 模型的模式演化能力较强。

  8. 面向对象数据库研究中的问题
    PDF 指出，OO 数据库研究中存在缺乏通用数据模型、缺乏理论基础、缺乏友好的用户界面与工具环境、缺乏有力的查询优化、商业上没有建立坚实基础等问题。

七、概念模型与数据库系统支持的数据模型的关系

  1. 两类数据模型
    一类是概念模型，用于表示信息结构，不涉及信息在计算机中的表示，典型代表是 E-R 模型；另一类是数据库系统支持的数据模型，包括层次数据模型、网状数据模型、关系数据模型、面向对象数据模型等。

  2. 从概念到实现的路径
    数据库设计通常先把现实世界抽象为概念模型，再把概念模型转换为某种具体的数据模型。这说明概念模型是设计起点，而关系模型、层次模型、网状模型等是实现层面的表达方式。

  3. 本章的核心逻辑
    本章实际上是在讲三件事：
    （1）怎样用 E-R 模型描述现实世界；
    （2）怎样理解不同逻辑数据模型的结构差异；
    （3）怎样把概念模型转换成关系模型并用约束保证正确性。

八、小结

  1. 本章最重要的结论
    数据模型分为概念模型和数据库系统支持的数据模型；概念模型中最重要的是 E-R 模型；数据库系统支持的数据模型中，层次模型、网状模型、关系模型、面向对象模型各有特点，但目前应用最广泛的是关系模型。

  2. E-R 模型的核心
    关键不是只会画图，而是要能准确识别实体、属性、联系，区分 1:1、1:n、m:n，理解实体内部联系、三元联系、弱实体、子类实体，并能将联系属性正确放到联系上。

  3. 关系模型的核心
    关系模型把现实世界统一映射为二维表，强调原子性、完整性约束和关系运算，是当前数据库系统的主流基础。

  4. 层次模型、网状模型、关系模型的关系
    层次模型是树，网状模型是图，关系模型是表；层次模型结构最简单但表达能力弱，网状模型表达能力更强但复杂，关系模型在表达能力、理论基础和使用便利性之间取得了最好平衡。

一、数据模型总论（+ 易错点）

核心结构回顾

  1. 数据模型 = 对现实世界数据特征的抽象

  2. 分类：

    • 概念模型（E-R）

    • 逻辑模型（层次 / 网状 / 关系 / OO）

    • 物理模型

  3. 三要素：

    • 数据结构（静态）

    • 数据操作（动态）

    • 完整性约束（规则）

易错点与分析

易错点1：混淆“概念模型”和“数据模型”

  • 错误理解：E-R模型也是DBMS直接使用的模型

  • 本质原因：没有区分“设计阶段”和“实现阶段”

✔ 正确理解：

  • E-R模型 → 用来“画世界”（设计）

  • 关系模型 → 用来“落地”（实现）

易错点2：三要素记不清 / 混淆

  • 常见错误：

    • 把“完整性约束”当成数据操作

    • 忘记“数据结构是核心”

✔ 正确记忆：

  • 静态：数据结构

  • 动态：数据操作

  • 规则：完整性约束

二、E-R 概念模型（+ 易错点重点）

核心结构回顾

  1. 基本概念：

    • 实体

    • 属性（型 + 值）

    • 联系（实体间 / 实体内部）

  2. 联系分类：

    • 按数量：1:1 / 1:n / m:n

第一部分：知识点整理（普通文本）

1. const 的核心作用

  • const 用于区分“可变”和“不可变”
  • 提供：
    • 类型安全（比 #define 更强）
    • 编译期检查
    • 程序稳定性

与 #define 的区别

  • #define：纯文本替换，无类型检查
  • const：
    • 有类型
    • 编译器可检查错误
    • 更安全

2. const 基本规则

  • const 变量必须初始化
  • 一旦初始化，不能修改

示例：

  • const int x = 10; ✔
  • const int x; ✘（未初始化）
  • x = 20; ✘（不可修改）

数组：

  • const int a[] = {1,2,3}
    • 每个元素都不可修改

3. const 与指针（重点）

判定原则

👉 const 修饰“离它最近的对象”

3.1 指向常量的指针（pointer to const）

定义：

  • const int* p
  • int const* p

特点：

  • 可以改指针指向
  • 不能改指针指向的值

示例：

  • p = &x ✔
  • *p = 10 ✘

3.2 常量指针（const pointer）

定义：

  • int* const p

特点：

  • 不能改变指针指向
  • 可以修改值

示例：

  • p = &y ✘
  • *p = 10 ✔

3.3 指向常量的常量指针

定义：

  • const int* const p

特点：

  • 不能改指向
  • 不能改值

总结
在 C/C++ 中，权限本质指的是“是否可以通过某个指针修改数据”。所谓“权限缩小”，就是把原本“可以修改”的对象，通过 const 限制为“不可修改”，这种行为是安全的，因此允许，例如 const int *p 指向变量，本质是“我选择不通过 p 修改它”；
因此指向常量的指针以及指向常量的常量型指针可以指向变量

而“权限放大”则是试图通过指针获得本不具备的修改能力（如用 int * 指向 const int），这会破坏数据的只读性，因此被禁止。

所有指针与常量的规则，本质都遵循一句话：👉 只能减少修改权限，不能增加修改权限；同时 const 只限制“指针的使用方式”，不会改变变量本身的属性，因此“指向常量的指针”“常量指针”“双 const 指针”本质都是在约束“能不能改值”和“能不能改指向”，而是否允许绑定某个对象，取决于是否违反了“不能放大权限”的原则。

  • 能改”的指针 ❌ 不能指向 const
  • “不改”的指针 ✅ 可以指向任何

一、构造函数（Constructor）

1. 基本概念

  • 构造函数是在对象创建时自动调用的函数，用于初始化对象。
  • 特点：

    • 没有返回值（连 void 都没有）

  • 对象创建时自动调用构造函数
  • 编译器隐式传入 this 指针（指向当前对象）

3. 带参数构造函数

  • 构造函数可以有参数
  • 可以用于初始化成员变量

示例思想：

  • 将传入参数赋值给成员变量
  • 实现对象初始化的灵活性

4. 构造函数重载

  • 一个类可以有多个构造函数（参数不同）
  • 编译器根据参数匹配调用对应构造函数

例如：

  • Student(int id)
  • Student(int year, int order)

1. 定义

  • 可以无参数调用的构造函数

2. 形式

  • 显式定义：A() {}
  • 或使用默认参数实现：A(int x = 0) 就可以实现额外传几个就改几个。其余的仍为默认值

  • 用于对象销毁时释放资源

2. 特点

  • 函数名：~类名
  • 无参数
  • 不能重载
  • 无返回值

    • 函数结束
    • delete（动态对象）

  2. 使用裸指针但未管理生命周期

一、核心考点总结（不重不漏版）

1️⃣ Access Control（访问控制）——核心基础

⭐ 两个本质目的（必考理论题）

  1. 保护数据（防止乱用）

  2. 实现实现隐藏（implementation hiding）

👉 关键词：

  • interface vs implementation

  • 抽象数据类型（ADT）

⭐ 三种访问控制（必考）

关键字 含义
public 所有人可访问
private 仅类内成员函数可访问
protected 类内 + 子类

👉 易考点：

  • 外部访问限制

  • 继承时访问权限

⭐ 类设计风格（容易考选择/判断）

👉 本质：

  • 接口在前 or 在后都可以

  • 但推荐：public → interface

2️⃣ Friend（重中之重🔥）

⭐ Friend 本质（三句话必背）

普通成员函数有 3 个属性：

  1. 能访问 private

  2. 属于类作用域

  3. 必须通过对象调用（this）

👉 friend 只有第 1 个

⭐ Friend 特性（高频选择题）

特性 是否成立
可访问 private ✅
是类成员 ❌
有 this 指针 ❌
受 public/private 控制 ❌

⭐ Friend 类型（必考分类）

  1. 普通全局函数
  1. 另一个类的成员函数

👉 难点：

  • 必须先声明类 B
  1. 整个类作为 friend

👉 含义：

  • B 可以访问 A 的所有 private

⭐ Friend 性质（必考概念题）

  • ❗ 非对称（asymmetric）

  • ❗ 不可传递（non-transitive）

  • ❗ 不可继承（non-inherited）

3️⃣ Static Members（静态成员）

⭐ 核心知识点

👉 特点：

  • 所有对象共享

  • 必须类外定义：

⭐ 访问方式

⭐ 高频考点

  • static 属于类，不属于对象

  • friend 可以访问 static private

4️⃣ Implementation Hiding（实现隐藏）

⭐ 核心思想（大题必考）

👉 接口不变，内部可以改

⭐ Handle / Cheshire（高阶考点🔥）

👉 本质：

技术 含义
前向声明 隐藏结构定义
指针 隐藏实现
cpp 中定义 真正实现

⭐ 优点（必考）

  1. 减少编译依赖

  2. 隐藏实现细节

  3. 提高可维护性

⭐ 缺点

  • 指针复杂

  • 内存管理问题

二、易错清单（高频丢分点🔥）

❌ 1. 误以为 friend 是成员函数（最常错）

错误认知：

friend 写在类里 → 就是类成员

正确：

  • friend 不是成员函数
  • 只是“被授权访问 private”

👉 直接后果：

  • ❌ 没有 this
  • ❌ 不能 obj.func()
  • ✅ 只能普通函数调用

❌ 2. 误以为 friend 受 public/private 控制

class A {
private:
friend void func(A&);
};

错误理解：

private → func 是私有函数

正确：

  • friend 不属于类
  • public/private 对它没有意义

❌ 3. 忘记 friend 仍然需要定义

class A {
friend void func(A&);
};

❗错误：

  • 以为已经完整

❗正确：

void func(A& a) {
// 必须定义
}

❌ 4. 成员函数作为 friend 的顺序问题（大坑🔥）

class Girl;

class Boy {
void show(Girl&);
};

class Girl {
friend void Boy::show(Girl&);
};

👉 易错点：

  • ❗必须先声明 Girl
  • ❗Boy 必须先有函数声明

否则编译错误

❌ 5. friend 非对称（必考）

class A {
friend class B;
};

❗错误理解：

A 和 B 互相访问

❗正确：

  • ✅ B 能访问 A
  • ❌ A 不能访问 B

❌ 6. friend 不可传递（考试超爱考）

A friend B;
B friend C;

❗错误：

C 可以访问 A

❗正确：

  • ❌ 不成立

❌ 7. friend 不可继承

class A {
friend class B;
};

class C : public B {};

❗错误：

C 也能访问 A

❗正确：

  • ❌ 不可以

❌ 8. static 成员误区

class A {
static int x;
};

❗常错：

  • ❌ 忘记类外定义
  • ❌ 认为属于对象

正确：

int A::x = 0;

❌ 9. static + friend 混淆

👉 friend 可以访问：

  • private 成员
  • static 成员

但：

👉 static 本质仍属于类

❌ 10. Cheshire / Handle（理解不到位）

class Handle {
struct Cheshire;
Cheshire* ptr;
};

❗错误理解：

只是 forward declaration

❗真正本质：

👉 隐藏实现（implementation hiding）

❌ 11. “访问权限 ≠ 可见性”

👉 很多人混淆：

概念 含义
可见性 编译器是否知道
访问权限 能不能用

👉 friend 是：

  • 可见 + 可访问

❌ 12. 误以为 private 不能被外部访问（绝对化错误）

❗错：

private 永远不能被外部访问

❗对：

  • friend 可以访问
  • 成员函数可以访问
