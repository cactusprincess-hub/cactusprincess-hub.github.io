第3章 关系数据库 复习整理

一、本章主线

关系数据库系统是支持关系模型的数据库系统。关系模型以集合论中的“关系”为基础，运用数学方法研究数据库的结构以及对数据的操作。本章围绕数据模型的三要素展开：数据结构、数据操作、完整性约束；并进一步学习关系模型的基本概念、关系代数、元组关系演算和域关系演算。

二、关系模型的基本概念

2.1 域（Domain）

域是一组具有相同数据类型的值的集合。它表示属性的取值范围。比如自然数、整数、{男，女}、{0，1} 都可以看作域；在教师关系中，姓名、性别、年龄也都可以分别对应一个域。

2.2 笛卡尔积（Cartesian Product）

给定若干集合 D1, D2, …, Dn，它们的笛卡尔积是所有分量组合形成的集合：
D1×D2×…×Dn = {(d1,d2,…,dn) | di∈Di}。
它的本质是“所有域的所有值的组合”，并且这些组合不重复。PDF 用“导师—专业—研究生”给出了三域笛卡尔积的完整例子。

2.3 元组（Tuple）与分量（Component）

笛卡尔积中的每一个元素称为一个元组；元组中的每一个值称为一个分量。比如 (张清玫, 计算机专业, 李勇) 是一个三元组，而“张清玫”“计算机专业”“李勇”分别是分量。

2.4 关系（Relation）

关系是笛卡尔积的任意一个子集。n 叫做关系的目或度。关系中的每一行对应一个元组，每一列对应一个属性。严格说，关系数据库中的关系必须是有限集合。

PDF 还特别强调：由于笛卡尔积本身不满足交换律，关系模型通过“属性名”来取消元组的有序性，因此在关系中列的顺序本质上是无关的。

2.5 规范化关系应满足的性质

规范化的关系有几个重要性质：
第一，列是同质的，即同一列的数据来自同一个域；第二，不同的列可以来自同一个域，但必须用不同属性名区分；第三，列的顺序无所谓；第四，元组不能重复；第五，行的顺序无所谓；第六，每个分量必须是原子值，不能再分。
其中“分量必须取原子值”是最基本、最重要的规范条件。PDF 还举了“职工工资”嵌套结构不符合关系模型要求的例子。

2.6 一元关系、二元关系

当 n=1 时称为一元关系；当 n=2 时称为二元关系。这个定义本身是关系理论中的基础概念，后面讲查询语言和运算时都会用到。

三、关系模式与关系数据库

3.1 关系模式（Relation Schema）

关系模式是对关系的描述，通常包括关系名、属性名、属性类型、长度以及属性间固有的数据联系。简记形式通常写作 R(A1, A2, …, An)。例如，图书关系模式可以写成：图书(书号, 书名, 作者, 单价, 出版社)。

3.2 关系的值

关系的值是元组的集合。一个关系模式在某一时刻对应的实际内容，就是该关系的值。PDF 强调，关系是现实世界某一时刻状态的反映，因此关系的值会随时间变化。

3.3 关系数据库与关系数据库模式

关系模式的集合称为关系数据库模式，通常写作 R={R1, R2, …, Rp}。每个关系模式上对应的关系集合，构成完整的关系数据库。

四、键（Key）

为了区分不同元组，需要用一个或多个属性值唯一标识元组，这样的属性或属性组称为关系的键。能够起标识作用而其子集不能起标识作用的键称为候选键；在多个候选键中选定一个作为主键；若键由多个属性组成，则称为联合键；若关系的所有属性都构成键，则称为全键。

这一部分的核心是：键的作用不是“好看”，而是“唯一标识元组”。后面的实体完整性、参照完整性，都建立在键的基础上。

五、完整性约束

关系模型中的完整性规则是对关系的约束条件。为了保证数据库中的数据与现实世界一致，关系数据库的插入、删除和修改操作必须受到约束。关系模型的三类完整性约束是：实体完整性、参照完整性、用户定义完整性。通常前两类由系统自动支持，用户定义完整性则反映具体应用的语义要求。

5.1 实体完整性

实体完整性要求主键的值不能为空或部分为空。换句话说，若属性 A 是基本关系 R 的主属性，则 A 不能取空值。原因是：如果键为空或部分为空，该元组就不可标识，也就不能表示任何实体。

PDF 进一步解释了实体完整性为什么成立：基本表通常对应一个实体集或多对多联系；现实世界中的实体是可区分的，关系模型用主键作为唯一标识，因此主键不能为空，否则就会出现不可区分的实体，这与实体可区分的现实相矛盾。

5.2 参照完整性

关系模型中实体及其联系都用关系表示，因此关系与关系之间自然存在引用。若关系 R1 中的属性 A 引用了关系 R2 的主键，则 R1 中 A 的值要么为空，要么必须等于 R2 中某个元组的主键值。

PDF 的学生—专业例子非常典型：学生关系中的“专业号”必须来自专业关系中真实存在的专业号，不能引用不存在的专业。这个规则就是参照完整性。

5.3 外键（Foreign Key）

若 F 是基本关系 R 的一个或一组属性，但不是 R 的键；并且 F 对应于基本关系 S 的主键 Ks，则称 F 为 R 的外键。R 是参照关系，S 是被参照关系或目标关系。R 和 S 不一定是不同的关系；外键与主键也不一定同名，但必须定义在同一个或一组域上。

PDF 还给出了“学生实体及其内部领导联系”的例子：学生关系中的“班长”属性值，如果非空，则必须是本关系中某个元组的学号值；这说明参照完整性不仅可以发生在不同关系之间，也可以发生在同一关系内部。

5.4 用户定义完整性

用户定义完整性是针对具体数据库的特殊约束，反映某一应用领域的语义要求。PDF 举例：选课关系中成绩不能为负数，或者某些数据输入格式需要满足特定限制。关系模型应提供统一的机制来定义和检验这类约束，而不应完全交给应用程序。

六、关系代数

6.1 关系代数是什么

关系代数是一种抽象查询语言，用对关系的运算来表达查询要求。它的三个要素是：运算对象是关系，运算结果也是关系，运算由一组运算符构成。关系代数是关系数据库系统中实现关系操作的重要基础。

6.2 关系代数的分类

关系代数分为三类：
第一，传统集合运算，包括并、差、交、广义笛卡尔积；
第二，专门的关系运算，包括选择、投影、连接、除法；
第三，扩充的关系运算，包括属性重命名、外连接。

关系操作的特点是“集合操作方式”，即操作对象和结果都是集合，属于“一次一集合”；而非关系数据模型通常是“一次一记录”。这是关系模型与传统记录式数据模型的根本区别之一。

七、传统集合运算

7.1 并（Union）

R∪S 仍为 n 目关系，由属于 R 或属于 S 的元组组成。前提是 R 和 S 具有相同的目数，并且对应属性来自同一个域。

7.2 差（Difference）

R-S 由属于 R 而不属于 S 的元组组成。同样要求两者具有相同目数和相应域匹配。

7.3 交（Intersection）

R∩S 由同时属于 R 和 S 的元组组成，也可表示为 R-(R-S)。

7.4 广义笛卡尔积

若 R 是 n 目关系，S 是 m 目关系，则 R×S 是一个 n+m 目关系，行数等于两者元组数的乘积。其本质是把 R 中每个元组与 S 中每个元组拼接。

八、专门的关系运算

8.1 选择（Selection）

选择是从关系中选择满足条件的元组子集，记作 σF(R)。F 是由逻辑连接词和比较表达式组成的布尔条件。选择从“行”的角度进行运算。

典型例子：
查询信息系学生：σSdept=’IS’(Student)
查询年龄小于 20 的学生：σSage<20(Student)。

8.2 投影（Projection）

投影是从关系中选出若干属性列组成新关系，记作 πA(R)。投影从“列”的角度进行运算，但它不仅会删除某些列，也可能删除重复元组。

例子：查询学生姓名和所在系，即 πSname,Sdept(Student)。

8.3 连接（Join）

连接是按条件把两个关系中的元组拼接起来形成新关系。最常见的是条件连接和自然连接。条件连接可写成 R ⋈AθB S，其中 A 和 B 为同域属性。等值连接是 θ 为“=”的情况。

自然连接是一种特殊的等值连接，要求被比较的分量是相同的属性组，并且结果中去掉重复属性列。PDF 强调，自然连接既涉及行，也涉及列。

8.4 除（Division）

除运算是一个二元运算，用符号 ÷ 表示。若 R(X,Y) 与 S(Y) 相关，则 R÷S 产生一个新关系 R’(X)，其含义是：找出那些在 X 上取值 x，使得 x 对应的“象集”包含了 S 在 Y 上的投影。直观上可以理解为“满足所有条件的那些对象”。

PDF 给了两个很经典的例子：

  1. 同时选修了 C2 和 C3 的所有学生；

  2. 选修了全部课程的学生号码和姓名。
    这类题几乎都是除法运算的标准应用场景。

8.5 属性重命名

属性重命名用来改变属性名，但不改变数据本身。它不仅可以对单个属性重命名，也可以对一组属性同时操作。其作用之一是便于同一关系做自然连接或笛卡尔积，也能把等值连接方便地表示为自然连接。

8.6 外连接

外连接是对自然连接的扩展，结果中除了满足连接条件的元组外，还包含没有被连接上的元组。左外连接保留左侧关系中未匹配的元组，右外连接保留右侧关系中未匹配的元组，完全外连接则是左右外连接的并。未匹配处通常用 NULL 填充。

九、关系代数中的典型例子

9.1 查询计算机系学生的学号和姓名

先选出计算机系学生，再投影学号和姓名：
πSno,Sname(σSdept=’计算机’(Student))。

9.2 查询选修了 2 号课程的学生学号

先在选课关系中选择 Cno=’2’，再投影 Sno：
πSno(σCno=’2’(SC))。

9.3 查询选修了 1 号课程的学生姓名

思路是：先连接 Student 和 SC，再筛选 Cno=’1’，最后投影 Sname。
这类题的关键不是直接背表达式，而是先问自己三件事：从哪里取数据、筛什么条件、最后保留哪些列。PDF 在这个例题里就是这样一步步展开的。

9.4 查询不选 1 号课的学生信息

先从 SC 中找出选了 1 号课的学号，再与 Student 做差集或差相关表达式，得到不选 1 号课的学生。这个例子用于训练“先找集合，再做差”的思路。

9.5 查询学生“刘明亮”选修的全部课程名

先连接 Student、SC、Course，再筛选 Sname=’刘明亮’，最后投影 Cname。PDF 还展示了利用属性重命名后做自然连接的写法，这个例子特别适合理解“为什么要先重命名”。

9.6 查询至少选修了其直接先行课为 5 号课的课程的学生姓名

这道题的关键是先从 Course 中筛出 Cpno=’5’ 的课程，再与 SC 和 Student 关联，最后投影学生姓名。PDF 还展示了通过中间关系再改写的等价形式，这说明复杂查询通常要拆成多个中间步骤。

9.7 查询选修全部课程的学生号码和姓名

这是除法运算的经典应用。思路是先用 πSno,Cno(SC) 除以 πCno(Course)，得到“选修了所有课程”的学生学号，再与 Student 连接取姓名。

9.8 插入、删除示例

插入示例是把学号 200504 的学生选修 4 号课、成绩 88 的记录加入 SC。删除示例则是删除学生“刘明亮”选修的英语课，并且要先考虑参照完整性，必要时先处理相关依赖记录。PDF 用这些例子说明：关系代数不仅可用于查询，也可用于更新表达。

9.9 利用重命名查询“与李勇在同一个系的学生”

PDF 的做法是先将 Student 自连接前重命名部分属性，然后做自然连接，再筛选李勇所在系，最后投影学号和姓名。这个例子非常适合理解重命名的必要性：如果不改名，自连接时属性名冲突会导致语义混乱。

十、关系代数的基本结论

关系代数可以用来完成查询、插入和删除等操作，其中查询是最重要的部分。关系代数中，并、差、笛卡尔积、选择、投影是基本运算；交、连接、除都可以由这些基本运算表示，因此引入它们并不增加语言能力，但可以简化表达。

十一、关系演算

11.1 关系代数语言与关系演算语言

关系代数语言用对关系的运算来表达查询要求，典型代表是 ISBL。关系演算语言则用谓词来表达查询要求，按谓词变元的基本对象不同，分为元组关系演算和域关系演算。

11.2 元组关系演算

元组关系演算语言以元组变量为基本对象。PDF 介绍了 ALPHA 和 QUEL，ALPHA 是由 Codd 提出的，QUEL 是 INGRES 所用语言，参考 ALPHA 研制，但并没有实际实现。

ALPHA 的基本格式是：
操作语句 <工作空间名>(表达式)：操作条件。
其中表达式可以是关系名或属性名，操作条件是一个逻辑表达式，可为空，还能附加排序要求、定额要求等。

ALPHA 的 GET 语句用于检索，例如：
GET W (SC.Cno)
GET W (Student)
GET W (Student.Sno, Student.Sage): Student.Sdept=’IS’ ∧ Student.Sage<20。

ALPHA 的更新语句包括 PUT、HOLD、UPDATE、DELETE、DROP。修改的标准步骤是：先用 HOLD 把元组读入工作空间，再用宿主语言修改，最后用 UPDATE 写回数据库。插入通常先在工作空间中构造新元组，再用 PUT 存入指定关系；删除则先 HOLD 再 DELETE。PDF 还给出了学生转系、插入课程、删除学生等完整例子。

11.3 域关系演算

典型的域关系演算语言是 QBE（Query By Example），由 M. M. Zloof 提出，并在 1978 年于 IBM 370 上实现。QBE 是基于屏幕表格的查询语言，通过填写表格构造查询，用示例元素表示结果可能情况，最终以表格形式输出结果。

QBE 的操作框架是：用户提出要求，系统显示空白表格，用户输入关系名，系统显示属性名，用户构造查询条件，最后显示结果。PDF 还给出了 QBE 的修改、插入、删除示例，如把 95001 学生年龄改为 18、把学生信息插入数据库、删除学生 95089 以及其选课记录等。

十二、关系数据语言的分类与特点

关系数据语言分为三类：关系代数语言、关系演算语言，以及同时具有关系代数和关系演算双重特点的语言。典型代表是 SQL。SQL 集 Query、DDL、DML、DCL 于一体，是关系数据库的标准语言。

关系数据语言的特点是高度非过程化，存取路径由 DBMS 优化机制决定，用户不必用循环结构完成操作，而且可以嵌入高级语言中使用。另一方面，关系代数、元组关系演算和域关系演算三者在表达能力上完全等价。

十三、关系运算的安全限制

由于集合论中的关系可以是无限的，而数据库中的关系必须是有限的，因此需要“安全限制”。不产生无限关系的关系表达式称为安全运算表达式。关系代数是安全的，只要输入关系有限，结果就有限；而关系演算不一定安全，因此需要加以限制。加上安全限制后，三种关系运算在表达能力上等价。

十四、概念结构与逻辑结构的对应

PDF 还给出了 E-R 模型与关系数据模型之间的对应关系：实体集对应关系表，实体集属性对应表的列，联系集与属性对应表和列，实体实例对应行，主键/候选键对应关系表中的主键/候选键。数据操作层面对应 SQL 语句、关系代数、关系演算；约束层面对应联系类型约束、键约束、完全参与约束以及关系模型中的三类完整性约束。

十五、本章最重要的专有名词清单

  1. 域：同类型值的集合。

  2. 笛卡尔积：多个域所有值组合形成的集合。

  3. 元组：关系中的一行。

1. Name Control 的核心目标

这一章讲的是如何控制“名字”的创建、可见性、存储位置和链接属性。课件把重点放在两类机制上：static 和 namespace。前者用于限制名字可见范围、改变存储方式，后者用于把全局名字拆分到更可管理的命名空间中。

2. static 的两个基本含义

static 有两个核心作用。第一，它可以控制名字的可见性，使该名字不能在翻译单元外或类外被看到；第二，它表示对象存储在静态数据区，而不是每次函数调用时都在栈上重新创建。也就是说，static 同时涉及“作用域/链接”与“存储期”两个层面。

3. 函数内 static 变量

函数内部的 static 局部变量会在多次函数调用之间保留值。它只在第一次执行到定义处时初始化一次，之后不会再次初始化。若是内置类型且没有写初值，编译器会保证它被初始化为 0。普通局部变量则每次调用都会重新创建并销毁。

4. 函数内 static 对象

函数内部的 static 用户自定义类型对象也是“只构造一次”。它的构造发生在第一次调用到该语句时，之后一直存在到程序结束。对于用户定义类型，如果没有提供初始化器，通常要求有默认构造函数。课件中的例子说明：static 对象的构造与析构时机，和普通局部对象完全不同。

5. 对象的构造与析构顺序

全局对象在进入 main() 之前就会被构造；函数内的 static 对象则只有函数被调用时才会构造。程序结束时，已经构造出来的对象会按照“构造的逆序”析构。课件里通过全局对象、static 局部对象和普通局部对象的组合，演示了析构顺序的差异。

6. static 数据成员

类中的 static 数据成员属于整个类，而不是某个具体对象。所有对象共享这一份存储空间。它必须在类外进行定义和初始化，写法通常是 int Myclass::obj = 8;，而且这里不再写 static。这类成员常用于表示“全类共享数据”。

7. static 成员函数

static 成员函数不依赖某个对象，因此没有隐含的 this 指针。它只能直接访问类的 static 数据成员，不能直接访问普通非静态成员。static 成员函数可以像普通函数一样通过类名调用，也可以在类内部直接定义，从而成为内联形式。

8. 链接属性与存储类型

课件把“可见性/链接”和“存储位置”分开讲：外部链接的名字可以在多个翻译单元中可见，普通全局变量和普通函数通常是外部链接；内部链接则只在本翻译单元可见，static、const、inline 名字通常默认具有内部链接。存储类型则常分为静态数据区、栈和堆，对应全局/静态对象、局部对象、new 创建的对象。

9. namespace 的作用

namespace 的目的，是把全局命名空间拆分成若干逻辑模块，减少大型项目中的名字冲突。命名空间里的名字不会直接污染全局空间，使用时可以通过作用域限定符访问，也可以通过 using 引入。

10. 命名空间的创建与使用

命名空间只能出现在全局作用域或另一个命名空间内部，不能像类一样创建对象；结尾也不需要分号。命名空间还可以起别名。使用命名空间时有两种常见方式：using directive 一次性引入整个命名空间的名字，using declaration 只引入某一个名字。

11. 作用域限定符的用途

作用域解析运算符 :: 可以用来定义或访问命名空间中的名字，也可用于类外定义类成员。课件中的例子展示了在命名空间中先声明类，再在外部定义其成员函数、嵌套类和普通函数的写法。

12. using 的两种方式

using namespace X; 会把整个命名空间引入当前作用域，适合小范围、短代码；using X::name; 只引入一个名字，更安全、更精确。课件还强调：在头文件里不要写全局 using directive，否则容易把名字污染到所有包含该头文件的文件中。

第二部分：易错点（普通文本）

1. 把 static 只理解成“变量不变”

很多人会把 static 简单理解成“值不变”，这是不完整的。课件强调 static 有两层意思：一层是名字的可见性/链接，一层是静态存储期。也就是说，static 的重点不是“常量”，而是“生命周期更长、可见范围更受控”。

2. 把 static 局部变量和普通局部变量混淆

普通局部变量每次进入函数都会重新创建；static 局部变量只初始化一次，并在多次调用间保留状态。课件里的例子里，n++ 会跨调用累加，而 x++ 每次都从 1 重新开始。

3. 忘记 static 内置类型默认置零

如果 static 内置类型没有显式初始化，编译器保证其被初始化为 0。很多人会误以为它是“随机值”，但课件明确给出了这个规则。这个点常用于判断程序第一次输出。

4. 误解 static 对象的构造和析构时机

函数内 static 对象不是每次进入函数都构造；它只在第一次执行到该语句时构造。析构也不是函数退出时发生，而是在程序结束时统一清理。这个差异是静态对象题的高频失分点。

5. 忘记静态成员必须类外初始化

static 数据成员只是“声明在类里”，真正的定义与初始化必须写在类外，而且不再写 static。如果只在类中声明而不在类外定义，链接阶段通常会出问题。

6. 把 static 成员函数当成普通成员函数

static 成员函数没有 this，所以不能直接访问普通非静态成员。它只能直接碰 static 成员。考试里经常通过“能不能访问某个变量”来考这个区别。

7. 混淆外部链接和内部链接

普通全局变量和函数通常是外部链接，能被多个翻译单元看到；static 名字通常只有内部链接。const 和 inline 名字也常默认表现为内部链接。这个点如果和“存储位置”混在一起，很容易答错。

8. 把 namespace 当成类

namespace 不能实例化，也不能像类那样有对象。它只是一个“名字容器”。很多同学会把“namespace 里能放类”误解成“namespace 本身也是一种类”，这是不对的。

9. using directive 和 using declaration 混用

using namespace calculator; 会把整个命名空间的名字都引入，可能导致重名和二义性；using calculator::Add; 只引入某个名字，更稳妥。课件还演示了引入整个命名空间后，调用 Print 可能和外部同名函数冲突。

10. 在头文件里写全局 using directive

课件明确提醒：不要在头文件里使用全局 using directive。因为头文件会被多个源文件包含，这会把命名空间里的名字无控制地扩散到全局作用域，造成命名冲突。

第一部分：知识点

1. Inline Function 的核心思想

Inline function（内联函数）的本质是：用函数的方式写代码，但在编译阶段像宏一样直接展开。

作用：

  • 消除函数调用开销（不需要压栈、跳转、返回）
  • 提高运行效率（尤其是小函数被频繁调用时）

例如：

inline int max(int a, int b) {
return a > b ? a : b;
}

调用：

max(a, b)

在编译时会被替换为：

(a > b ? a : b)

2. Inline vs 宏（#define）

（1）宏的本质

宏是纯文本替换（预处理阶段），没有语法检查。

#define MAX(a, b) a > b ? a : b

问题示例：

int c = MAX(a, b) + 2;

实际展开为：

a > b ? a : b + 2

优先级错误，导致结果不符合预期。

（2）宏的缺点

  1. 容易产生隐藏 Bug（优先级问题）
  2. 没有类型检查
  3. 不能作为类成员函数
  4. 调试困难

（3）Inline 的优势

Inline 函数：

  • 有类型检查
  • 符合函数语义
  • 可以作为类成员函数
  • 编译器可优化

👉 结论：C++ 中应优先使用 inline，避免使用宏

3. Inline 的工作机制

编译器处理 inline 函数时：

  • 保存函数类型（函数签名）
  • 同时保存函数体
  • 在调用处尝试展开

但注意：
👉 inline 只是建议（hint），编译器可以拒绝

当函数很短但调用很多次时，用 inline 可以减少函数调用开销，提高效率。
inline 函数会在编译时像宏一样展开，从而避免函数调用过程。
但相比宏，inline 更安全，所以应尽量用 inline 代替宏。

✅ 最后一句总结（建议记）

👉 inline 是“带类型检查的宏替代方案”，用于减少小函数调用开销，但是否展开由编译器决定

inline 需要在编译阶段展开，而编译是按文件独立进行的，所以函数体必须在当前文件可见，通常放在头文件中

4. Inline 的使用规则（考试重点）

（1）定义必须在调用之前

因为编译器需要看到函数体才能展开。

（2）适用于小函数

适合：

  • 简单计算函数
  • getter/setter
  • 短逻辑

（3）不适合的情况

一般不会被 inline：

  • 含循环（for / while）
  • 含 switch
  • 含异常处理
  • 递归函数
  • 代码过大

5. Inline 在类中的使用

（1）类内定义（自动 inline）

public:

// 自动 inline
}
};

👉 在类内部定义的函数默认 inline

（2）类外定义（需要显式 inline）

class Point {
public:
void print() const;
};

inline void Point::print() const {
// 需要 inline 关键字
}

👉 原因：
类外定义默认不是 inline，需要手动声明

6. Inline vs 宏的典型代码对比

宏：

#define f(x) xx
f(x+1) → x+1x+1 → 错误

Inline：

inline int f(int x) {
return xx;
}
f(x+1) → (x+1)(x+1) → 正确

👉 本质区别：

  • 宏：文本替换
  • inline：语法级函数展开

7. Inline 的限制（重要）

  1. 代码过大 → 编译器不会展开
  2. 取函数地址 → 无法 inline
  3. 复杂控制流 → 无法 inline

8. Inline 的使用建议（总结）

  • 小函数 + 高频调用 → 用 inline
  • 复杂逻辑 → 普通函数
  • 不要用宏替代函数

一、数据模型总论

  1. 数据模型的定义
    数据模型是用来抽象、表示和处理现实世界中的数据和信息的工具，本质上是对现实世界数据特征的抽象。它是数据库研究中的核心问题之一。

  2. 数据模型的两层含义
    广义上，数据模型是数据库研究的核心；狭义上，每个 DBMS 都建立在某种具体的数据模型之上。PDF 指出，常见的传统数据模型包括层次模型、网状模型和关系模型。

  3. 数据模型的分类
    数据模型按应用目的可分为两类：
    （1）概念模型，也称信息模型，按用户观点对数据和信息建模，主要用于数据库设计。
    （2）数据模型，按计算机系统观点对数据逻辑结构建模，主要用于 DBMS 实现。其下又可分为逻辑数据模型和物理数据模型。逻辑数据模型包括层次模型、网状模型、关系模型、面向对象模型、对象关系模型等；物理数据模型描述数据在系统内部的表示方式和存取方法。

  4. 数据模型的三个要素
    数据模型通常由数据结构、数据操作、完整性约束三个要素组成。
    （1）数据结构：描述数据库的组成对象及对象之间的联系，是刻画数据模型性质最重要的方面。
    （2）数据操作：描述对数据库对象实例允许执行的操作集合，包括检索、插入、删除、修改等，同时要定义操作的含义、符号、规则及语言。
    （3）完整性约束条件：一组完整性规则，用于限定符合数据模型的数据库状态及状态变化，保证数据正确、有效、相容。

  5. 静态与动态特性
    数据结构描述系统静态特性；数据操作描述系统动态特性。完整性约束则是保证系统状态合法的规则体系。

二、E-R 概念模型

  1. 概念模型的作用
    概念模型用于信息世界建模，是现实世界到机器世界之间的中间层次，也是数据库设计的有力工具和数据库设计人员与用户之间交流的语言。它的要求是语义表达能力强，同时简单、清晰、易于理解。E-R 模型是最著名的概念模型。

  2. E-R 模型的三大基本概念
    （1）实体（Entity）：客观存在并可相互区别的事物，可以是具体对象，也可以是抽象概念。
    （2）属性（Attribute）：实体具有的某一特征，用来刻画实体。属性有“型”和“值”之分，属性名是型，具体内容是值。
    （3）联系（Relationship）：现实世界中事物内部以及事物之间的联系，在信息世界中抽象为实体内部的联系和实体之间的联系。

  3. 联系的基本类型
    （1）一对一联系（1:1）：实体集 A 中一个实体至多对应实体集 B 中一个实体，反之亦然。例子是“班级与班长”，一个班级只有一个正班长，一个班长只在一个班中任职。
    （2）一对多联系（1:n）：实体集 A 中一个实体对应实体集 B 中的多个实体，反过来一个 B 中实体至多对应一个 A 中实体。例子是“班级与学生”，一个班级中有若干学生，一个学生只在一个班级中学习。
    （3）多对多联系（m:n）：实体集 A 中一个实体对应实体集 B 中多个实体，反之亦然。例子是“课程与学生”，一门课程有若干学生选修，一个学生也可选修多门课程。

  4. 多元联系
    两个以上实体集之间也可以存在联系，称为多元联系。PDF 以“供应商—零件—工程”为例，说明三者之间存在 m:n:p 的联系，表达的是“某个供应商供应某种零件给某个工程”。

  5. 三元联系与二元联系的区别
    这是本章非常关键的细节。PDF 明确指出，三个实体集两两之间的多对多联系，只能表示“一个工程需要哪些零件”“这些零件可以由哪些供应商供应”，却不能表示“一个工程所用的零件具体由哪个供应商供应”以及“一个供应商具体供应哪种零件给哪个工程”。因此，三元联系不能简单拆成三个二元联系，否则会丢失语义。

  6. 同一实体集内部的联系
    PDF 还强调，联系不只存在于不同实体集之间，同一实体集内部也可以有联系。典型例子是职工实体集内部的“领导与被领导”关系：某一职工可以领导若干职工，而一个职工仅被另一个职工直接领导，这是同一实体型内部的一对多联系。PDF 也提到，同一实体集内部还可能存在一对一联系和多对多联系。

  7. E-R 图的表示方法
    E-R 图有三个基本成分：实体、属性和联系。
    （1）实体用矩形表示，矩形框内写实体名。
    （2）属性用椭圆表示，并用无向边与对应实体连接。
    （3）联系用菱形表示，菱形框内写联系名，再用连线把关联实体连接起来，并在连线旁标明联系类型 1:1、1:n 或 m:n。

  8. 联系的属性
    联系本身也可以有属性。PDF 的“选课”例子中，成绩是联系“选课”的属性，而不是学生实体或课程实体的属性，因为成绩描述的是“学生选修某门课程”这个联系。

  9. 弱实体
    弱实体是一类特殊实体，它的存在依赖于其他实体而存在。与弱实体相对应，所依赖的实体称为强实体。弱实体在 E-R 模型中用双框矩形表示，与菱形联系间用双线连接，以表示全部参与。PDF 举例说，在学生管理信息中，家长实体依赖学生实体存在，因此家长可视为弱实体。

  10. 子类实体
    扩展 E-R 模型中增加了子类和超类概念，使模型更有语义表达能力。一个实体集中的个体可以根据不同特性划分为多个子集。PDF 的例子是学校一个系的职工可分为教师、实验人员和机关工作人员，它们共享姓名、年龄、性别等共同属性，同时又有各自的特殊属性。

  11. E-R 模型的用途与特点
    E-R 模型广泛用于数据库概念模型设计。它只表示现实世界中的信息结构及信息之间的关系，不涉及信息在计算机中的表示；只要用户需求不变，E-R 模型是稳定的，并且可以方便地转换成具体 DBMS 支持的数据模型。

  12. PDF 中的综合建模例子
    工厂物资管理模型是本章最完整的例子之一。它涉及五类实体：仓库、零件、供应商、项目、职工。
    （1）仓库：仓库号、面积、电话号码。
    （2）零件：零件号、名称、规格、单价、描述。
    （3）供应商：供应商号、姓名、地址、电话号码、账号。
    （4）项目：项目号、预算、开工日期。
    （5）职工：职工号、姓名、年龄、职称。
    这些实体之间的联系包括：仓库和零件是 m:n 联系，联系属性为库存量；仓库和职工是 1:n 联系；职工内部存在领导与被领导的一对多联系；供应商、项目和零件三者之间存在多对多的三元联系。这个例子综合体现了本章几乎所有 E-R 概念。

三、层次数据模型

  1. 层次模型的定义
    层次模型是数据库系统中最早出现的数据模型，典型代表是 IBM 的 IMS。它用树型结构表示各类实体及实体间联系。现实世界中许多关系具有天然层次性，例如家族关系和行政机构。

  2. 层次模型的结构条件
    满足下面两个条件的基本层次联系集合构成层次模型：
    （1）有且只有一个结点没有双亲结点，该结点称为根结点。
    （2）根以外的其他结点有且只有一个双亲结点。

  3. 层次结构中的术语
    根结点位于最上层；其他结点的上一级结点称为双亲结点；同一双亲结点的子女结点称为兄弟结点；没有子女的结点称为叶结点。双亲结点到子女结点之间表示记录间的一对多联系。

  4. 层次模型的优点
    结构简单清晰；查询效率高；提供较好的数据完整性支持。

  5. 层次模型的缺点
    不能直接表示两个以上实体型间的复杂联系和实体型间的多对多联系，通常要通过引入冗余数据或虚拟结点来解决，容易产生不一致性；插入和删除操作限制较多；查询子女结点必须通过双亲结点；由于结构严密，层次命令趋于程序化。

四、网状数据模型

  1. 网状模型的定义
    网状模型用有向图表示实体及实体间的联系，是对层次模型局限性的突破。现实世界中的许多事物之间是非层次关系，因此网状模型比层次模型更接近实际。

  2. 网状模型的结构条件
    基本网状模型满足两个条件：
    （1）允许一个以上的结点没有双亲。
    （2）一个结点可以有多于一个的双亲。

  3. 网状模型与层次模型的关系
    PDF 明确指出，层次模型实际上是网状模型的特例。两者从结构上看，层次模型是树，网状模型是图；当多个结点都可以有多个双亲时，有向树就变成了有向图。

  4. 网状模型的优点
    能更直接地描述现实世界，例如一个结点可以有多个双亲；性能较好，存取效率较高。

  5. 网状模型的缺点
    结构复杂，随着应用环境扩大，数据库结构会越来越复杂，不利于最终用户掌握；DDL、DML 语言复杂，用户不容易使用；访问数据时必须自行选择存取路径，增加程序编写负担。

  6. 网状模型如何表示多对多联系
    PDF 提到，网状模型可以间接表示多对多联系，方法是将多对多联系分解成一对多联系，并用联结记录来处理。

五、关系数据模型

  1. 关系模型的重要地位
    关系模型是最重要的数据模型。E.F. Codd 于 1970 年系统而严格地提出关系数据模型，并随后提出关系代数、关系演算以及关系范式理论，奠定了现代数据库的理论基础，1981 年因此获得图灵奖。

  2. 关系数据库的发展
    PDF 提到，1977 年 IBM 的 System R 开始运行，后来出现了基于 System R 的 SQL/DB。20 世纪 80 年代以来，几乎所有数据库管理系统都支持关系模型，非关系系统也增加了关系接口；当前数据库研究工作也以关系方法为基础，关系数据库成为最广泛应用的数据库系统。

  3. 关系模型的基本结构
    关系模型中，基本数据结构被限制为二维表，一张二维表称为一个关系。一个关系可用于描述一个实体集。

  4. 关系模型中的基本术语
    （1）关系（relation）：二维表，由行和列组成。
    （2）属性（attribute）：关系中的一列。
    （3）域（domain）：某属性的取值集合，即属性的取值范围。
    （4）元组（tuple）：关系中的一行，表示实体集中的一个个体。
    （5）键（key）：一个或多个属性组成，能够唯一标识一个元组。一个关系中可能有多个键，其中选定一个为主键，其余为候选键。

  5. 关系模式
    对关系结构的描述称为关系模式，形式通常写作“关系名(属性名1, 属性名2, …, 属性名n)”。例如学生关系可表示为“学生(学号, 姓名, 出生年月, 性别, 入学年份, 班级)”。关系数据库模式是一组关系模式的集合，而这些关系模式对应的关系集合构成关系数据库。

  6. 关系模型中实体与联系的表示
    关系模型中，基本数据结构是单一的关系，现实世界中的实体以及实体间的联系都用关系表示。E-R 模型中的联系在关系模式中也可以用表表示，例如“选课”联系可用“选课(学号, 课程号, 成绩)”表示，其中成绩是联系自身的描述属性。

  7. 关系模型的规范化要求
    关系必须规范化，最基本的规范条件是：关系的每一个分量必须是一个不可分的数据项。PDF 用“职工工资”表说明，如果一个属性中又包含“基本工资、工龄、职务、房租、水电”等嵌套成分，就不符合关系模型要求。

  8. 关系模型的数据完整性约束
    为维护数据库与现实世界的一致性，需要对数据施加约束条件。关系模型中主要有三类完整性约束：实体完整性、参照完整性、用户自定义完整性。

  9. 关系模型的数据操纵
    关系模型中的数据操作包括查询、插入、删除和修改。关系数据库系统中对数据的全部操作都可以归结为关系运算；关系运算结果形成一个新关系；关系运算分为关系代数和关系演算。

  10. 关系模型的优点
    PDF 归纳的关系模型优点包括：数据结构简单；一体化的数据子语言；数据独立性高；面向集合的存取方式；理论基础坚实；有利于开展其他应用。

  11. 概念模型与关系数据模型的对应
    PDF 给出了一组非常重要的对应关系：
    （1）E-R 模型中的实体集对应关系表。
    （2）实体集属性对应表的列。
    （3）联系集及其属性也可对应表和列。
    （4）实体的实例对应表中的各行。
    （5）主键或候选键对应关系表中的主键或候选键。
    （6）数据操作在实现层面对应 SQL 语句，在理论层面对应关系代数和关系演算。
    （7）联系类型约束、键约束、完全参与约束在关系模型中分别对应实体完整性、参照完整性和用户自定义完整性。

六、面向对象数据模型

  1. 面向对象数据库系统的两条路线
    PDF 指出，对象关系数据库系统 ORDBS 是面向对象数据模型和关系数据模型结合的产物。研究路线有两条：一是建立新的面向对象数据库系统 OODB，直接支持 OO 数据模型；二是以关系数据库和 SQL 为基础，把面向对象技术融入数据库系统，形成 ORDBS。

  2. 对象的定义
    对象是由一组数据结构和在这组数据结构上的操作程序代码封装起来的基本单位。对象由属性集合和方法集合构成：属性描述状态、组成和特性，方法描述行为特性。

  3. OID
    OID 是对象标识符，即每个对象都有一个唯一且不变的标识。它具有永久持久性、独立于值、系统全局唯一等特点。

  4. 封装
    封装是对象的外部界面与内部实现之间实行清晰隔离的一种抽象，外部与对象的通信只能通过消息。对象封装后，查询属性值必须通过调用方法。

  5. 类
    类是共享同样属性和方法集的所有对象构成的集合。对象是某一类的实例，在 OODB 中，类是“型”，对象是某一类的“值”。

  6. 类层次结构
    PDF 以“教员、行政人员、工人继承教职员工类和人的属性与方法”为例，说明面向对象模型中存在类层次结构；子类在逻辑上继承父类的所有属性和方法，同时还拥有自身特有的属性和方法。

  7. 关系模型与 OO 模型的比较
    PDF 从多个角度对比两者：关系模型的基本数据结构是二维表，OO 模型是类；关系模型使用码作为标识，OO 模型使用 OID；关系模型的动态行为用关系操作描述，OO 模型用方法描述；OO 模型支持抽象数据类型和封装，而关系模型没有；关系模型主要依赖主外码联系和数据依赖，OO 模型则强调继承和组合；OO 模型的模式演化能力较强。

  8. 面向对象数据库研究中的问题
    PDF 指出，OO 数据库研究中存在缺乏通用数据模型、缺乏理论基础、缺乏友好的用户界面与工具环境、缺乏有力的查询优化、商业上没有建立坚实基础等问题。

七、概念模型与数据库系统支持的数据模型的关系

  1. 两类数据模型
    一类是概念模型，用于表示信息结构，不涉及信息在计算机中的表示，典型代表是 E-R 模型；另一类是数据库系统支持的数据模型，包括层次数据模型、网状数据模型、关系数据模型、面向对象数据模型等。

  2. 从概念到实现的路径
    数据库设计通常先把现实世界抽象为概念模型，再把概念模型转换为某种具体的数据模型。这说明概念模型是设计起点，而关系模型、层次模型、网状模型等是实现层面的表达方式。

  3. 本章的核心逻辑
    本章实际上是在讲三件事：
    （1）怎样用 E-R 模型描述现实世界；
    （2）怎样理解不同逻辑数据模型的结构差异；
    （3）怎样把概念模型转换成关系模型并用约束保证正确性。

八、小结

  1. 本章最重要的结论
    数据模型分为概念模型和数据库系统支持的数据模型；概念模型中最重要的是 E-R 模型；数据库系统支持的数据模型中，层次模型、网状模型、关系模型、面向对象模型各有特点，但目前应用最广泛的是关系模型。

  2. E-R 模型的核心
    关键不是只会画图，而是要能准确识别实体、属性、联系，区分 1:1、1:n、m:n，理解实体内部联系、三元联系、弱实体、子类实体，并能将联系属性正确放到联系上。

  3. 关系模型的核心
    关系模型把现实世界统一映射为二维表，强调原子性、完整性约束和关系运算，是当前数据库系统的主流基础。

  4. 层次模型、网状模型、关系模型的关系
    层次模型是树，网状模型是图，关系模型是表；层次模型结构最简单但表达能力弱，网状模型表达能力更强但复杂，关系模型在表达能力、理论基础和使用便利性之间取得了最好平衡。

1. const 的核心作用

  • const 用于区分“可变”和“不可变”
  • 提供：

  • const 变量必须初始化
  • 一旦初始化，不能修改

  • const int x = 10; ✔

数组：

定义：

  • int* const p

特点：

  • 不能改变指针指向
  • 可以修改值

示例：

  • p = &y ✘
  • *p = 10 ✔

3.3 指向常量的常量指针

定义：

  • const int* const p

特点：

  • 不能改指向
  • 不能改值

总结
在 C/C++ 中，权限本质指的是“是否可以通过某个指针修改数据”。所谓“权限缩小”，就是把原本“可以修改”的对象，通过 const 限制为“不可修改”，这种行为是安全的，因此允许，例如 const int *p 指向变量，本质是“我选择不通过 p 修改它”；
因此指向常量的指针以及指向常量的常量型指针可以指向变量

而“权限放大”则是试图通过指针获得本不具备的修改能力（如用 int * 指向 const int），这会破坏数据的只读性，因此被禁止。

所有指针与常量的规则，本质都遵循一句话：👉 只能减少修改权限，不能增加修改权限；同时 const 只限制“指针的使用方式”，不会改变变量本身的属性，因此“指向常量的指针”“常量指针”“双 const 指针”本质都是在约束“能不能改值”和“能不能改指向”，而是否允许绑定某个对象，取决于是否违反了“不能放大权限”的原则。

  • 能改”的指针 ❌ 不能指向 const
  • “不改”的指针 ✅ 可以指向任何

4.1 参数中的 const

目的：
👉 防止函数修改外部数据

  • void f(const int* p)
    • *p 不可修改

4.2 返回值中的 const

目的：
👉 防止调用者修改返回对象

示例：

合法 因为虽然p被复制了一个限制地址的指针 但本质是复制 失效。所以可以被重新修改地址

  • int* const w(); 里的 const 限制的只是函数内部的那份指针
  • 函数返回时，你拿到的是拷贝，所以外部的变量 p 不再受原来的 const 限制
  • 也就是 “指针本身的 const 在返回值上失效”

第一部分：知识点（普通文本）

一、构造函数（Constructor）

1. 基本概念

  • 构造函数是在对象创建时自动调用的函数，用于初始化对象。
  • 特点：
    • 函数名与类名相同
    • 没有返回值（连 void 都没有）
    • 在对象定义时自动调用

2. 调用机制

  • 对象创建时自动调用构造函数
  • 编译器隐式传入 this 指针（指向当前对象）

3. 带参数构造函数

  • 构造函数可以有参数
  • 可以用于初始化成员变量

示例思想：

  • 将传入参数赋值给成员变量
  • 实现对象初始化的灵活性

4. 构造函数重载

  • 一个类可以有多个构造函数（参数不同）
  • 编译器根据参数匹配调用对应构造函数

例如：

  • Student(int id)
  • Student(int year, int order)

二、默认构造函数（Default Constructor）

1. 定义

  • 可以无参数调用的构造函数

2. 形式

  • 显式定义：A() {}
  • 或使用默认参数实现：A(int x = 0) 就可以实现额外传几个就改几个。其余的仍为默认值

3. 注意事项

  • 如果定义了带参数构造函数，而没有默认构造函数：
    • 编译器不会自动生成默认构造函数
    • 会导致无法无参创建对象

4. 成员对象影响

  • 类成员对象会先调用其构造函数
  • 若成员类没有默认构造函数，会导致错误

三、析构函数（Destructor）

1. 基本概念

  • 用于对象销毁时释放资源

2. 特点

  • 函数名：~类名
  • 无参数
  • 不能重载
  • 无返回值

3. 调用时机

  • 对象生命周期结束时自动调用：
    • 作用域结束
    • 函数结束
    • delete（动态对象）

4. 调用顺序

  • 构造：先成员 → 后自身
  • 析构：先自身 → 后成员（逆序）

四、构造与析构的执行过程

1. 局部对象

  • 进入作用域：构造
  • 离开作用域：析构

2. 嵌套调用

  • 函数中创建对象：
    • 函数结束立即析构

3. 示例核心逻辑

  • 对象按栈顺序创建
  • 按逆序销毁（类似栈）

  1. 有没有 new？
    有 → 堆对象

  2. 在不在函数里？
    在 → 局部对象（栈）。作用域与函数的生命周期绑定

  3. 在类里面？
    是 → 成员对象。 和这个类的周期绑定。

  4. 在函数外？
    是 → 全局对象。和程序的运行周期绑定

  5. 有 static？
    是 → 静态对象
    对象什么时候死，不看它写在哪个文件，
    只看它在哪个作用域里被“创建”。

对于局部对象

真的是栈（物理结构）

对于其他对象

不是栈，但遵循“栈式规则”

  2. 使用裸指针但未管理生命周期
